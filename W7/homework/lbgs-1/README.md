## 2. 快排代码（要求 1）

核心是课件给的“首元素基准 + 两个列表推导式 + 拼接”，只多加了可选的 `depth` / `log` 参数用来记录递归层数（正常调用 `quick_sort(arr)` 行为不变）：

```python
def quick_sort(arr, depth=0, log=None):
    if log is not None:
        log.append((depth, len(arr)))
    if len(arr) <= 1:                       # Base Case
        return arr
    pivot = arr[0]
    left = [x for x in arr[1:] if x < pivot]    # 必须用 arr[1:]，排除基准本身
    right = [x for x in arr[1:] if x >= pivot]
    return quick_sort(left, depth + 1, log) + [pivot] + quick_sort(right, depth + 1, log)
```

两个可选版本（弹性挑战里的要求）：

| 函数 | 基准选法 | 分区方式 | 解决的问题 |
|:---|:---|:---|:---|
| `quick_sort` | `arr[0]`（首元素） | 两路：`< pivot` / `>= pivot` | 必做版 |
| `quick_sort_random` | `random.choice(arr)` | 三路：`< pivot` / `== pivot` / `> pivot` | 已排序输入退化、大量重复元素 |
| `quick_sort_3way` | `arr[0]` | 三路：`< pivot` / `== pivot` / `> pivot` | 只解决“重复元素”，基准仍可能退化 |

## 3. 退化测试记录（要求 2）

**输入**：`[1, 2, 3, 4, 5, 6, 7, 8]`（本身就是有序列表），首元素作基准。在每次调用时记录 `(当前层数, 当前子列表长度)`，实测输出：

```
[退化测试] 输入 [1, 2, 3, 4, 5, 6, 7, 8]（已排序），首元素作基准
  第 0 层：子列表长度 [8]
  第 1 层：子列表长度 [0, 7]
  第 2 层：子列表长度 [0, 6]
  第 3 层：子列表长度 [0, 5]
  第 4 层：子列表长度 [0, 4]
  第 5 层：子列表长度 [0, 3]
  第 6 层：子列表长度 [0, 2]
  第 7 层：子列表长度 [0, 1]
  → 调用层数（含最外层）= 8，最大递归深度 = 7
```

整理成表：

| 层数 | 子列表长度 | 说明 |
|:---|:---|:---|
| 0 | 8 | 整个列表，基准 1 |
| 1 | 0、7 | `left` 为空（没有元素 < 1）；`right` 有 7 个 |
| 2 | 0、6 | 基准 2，同上 |
| 3 | 0、5 | 基准 3 |
| 4 | 0、4 | 基准 4 |
| 5 | 0、3 | 基准 5 |
| 6 | 0、2 | 基准 6 |
| 7 | 0、1 | 基准 7，剩 `[8]` 是 Base Case |

**最大递归层数 = 7**（若把最外层调用也算作一层，则共 8 层，即深度 $n$ 而不是 $\log_2 8 = 3$）。

**退化原因**

1. 列表已排序，`pivot = arr[0]` 永远是当前子列表的**最小值**；
2. 于是 `left = [x for x in arr[1:] if x < pivot]` 恒为空列表，所有剩下的元素都进 `right`；
3. `right` 的长度只比原来少 1（少了基准本身），所以递归深度 = $n$ 层；
4. 每层只排好 1 个元素，总比较/复制次数约为 $n + (n-1) + \dots + 1 = n(n+1)/2$，时间复杂度退化为 $O(n^2)$（$n=8$ 时 36 次，看似无害；$n$ 大时才致命）。

**耗时对照**（已排序输入，首元素基准 vs 随机化基准，每档取 3 轮最快）：

| n | 首元素基准 | 随机化基准 |
|:---|:---|:---|
| 200 | 1.028 ms | 0.159 ms |
| 400 | 4.605 ms | 0.364 ms |
| 800 | 18.090 ms | 0.793 ms |

$n$ 每翻一倍，首元素基准耗时约 ×4.5、×3.9（二次增长，符合 $O(n^2)$）；随机化基准约 ×2.3、×2.2（接近 $O(n\log n)$）。（单次实测，具体毫秒数随机器波动，倍数关系稳定。）加 `--slow` 会多测一档 `n=1600`：首元素基准 70.820 ms、随机化基准 1.693 ms，倍数仍是约 ×4。

**修正方式**：`pivot = random.choice(arr)`（本文件 `quick_sort_random`）。同一已排序输入跑 20 次，随机化基准的递归深度为最小 3、平均 3.9、最大 5 —— 期望是 $\log_2 8 = 3$ 左右，但只有 8 个元素时样本太小，偶尔抽到坏基准仍会变深；数据量越大越接近 $O(\log n)$。

## 4. 手工分区结果（要求 3）

给定 `[8, 3, 5, 1, 7, 2, 9, 4]`，基准值 `5`，逐个判断：

| 元素 | < 5 ? | 归入 |
|:---|:---|:---|
| 8 | 否 | right |
| 3 | 是 | left |
| 5 | —（等于基准，单独放） | pivot |
| 1 | 是 | left |
| 7 | 否 | right |
| 2 | 是 | left |
| 9 | 否 | right |
| 4 | 是 | left |

**分区结果**

| | 列表 |
|:---|:---|
| **left**（< 5） | `[3, 1, 2, 4]` |
| **pivot** | `[5]` |
| **right**（≥ 5） | `[8, 7, 9]` |

**基准的最终位置**：`left` 有 4 个元素，所以 `5` 排在下标 **4**（即第 5 个位置）；拼接后 `[3,1,2,4] + [5] + [8,7,9]` = 8 个元素，与原列表长度一致。整表排序结果是 `[1,2,3,4,5,7,8,9]`，`5` 也确实在下标 4 —— **分区完成后基准已经在它的最终位置上**，不需要再参与后续递归（这正是快排“先分后排”、与归并“先排后合”的关键差别）。

验证：`left` 全部 `< 5` 为 True，`right` 全部 `>= 5` 为 True（脚本里实际断言过）。

## 5. 一个快排的坑（要求 4）

**坑：分区时用了 `arr` 而不是 `arr[1:]` —— 基准重复进入 `right`，导致无限递归**

错误的写法：

```python
def quick_sort_wrong(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[0]
    left = [x for x in arr if x < pivot]      # 错：应为 arr[1:]
    right = [x for x in arr if x >= pivot]    # 基准又进了 right
    return quick_sort_wrong(left) + [pivot] + quick_sort_wrong(right)
```

**现象**：`quick_sort_wrong([3, 1, 2])` 并不返回结果，而是抛

```
RecursionError: maximum recursion depth exceeded
```

**原因**：`right` 用 `arr` 过滤且条件是 `>= pivot`，基准自己满足条件，于是 `right` 里又出现了 `pivot`；`len(right) == len(arr)`，每层递归长度不减少，永远收敛不到 `len(arr) <= 1` 的 Base Case。Python 默认递归上限 1000 层，很快就撞上上限报错（在别的语言里就是栈溢出）。

**修正**：两个列表都用去掉首元素的切片，保证基准只出现一次：

```python
left = [x for x in arr[1:] if x < pivot]
right = [x for x in arr[1:] if x >= pivot]
```

或者按课件随机化版本，把 `== pivot` 单独放进 `equal`（`left`/`right` 也用完整的 `arr`，但 `equal` 接住了基准，长度同样会减少）。

**连带的另一个坑**：如果 `right` 写成 `> pivot` 而不是 `>= pivot`，等于基准的元素既不在 `left` 也不在 `right`，**元素会被丢掉**（结果变短且排序错误）。简洁版必须用 `>= pivot`，或者像三路分区那样用 `equal` 接住。
